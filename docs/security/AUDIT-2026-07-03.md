**Date:** 2026-07-03
**Auditor:** Exilio (security engineer persona)
**Scope:** 11 API endpoints, 30+ RLS policies, payment flow, auth flow
**Method:** Source review + DB introspection + behavior analysis

## 🚨 CRITICAL (C1-C3) — Database-level leaks

### C1. `user_identities` table — PUBLIC CRUD
```sql
policy: service_role_crud | qual: true | with_check: true
```
**Bahaya:** Semua authenticated user bisa SELECT email + internal_id mapping siapa aja. INSERT/UPDATE/DELETE juga tanpa batas. Attacker bisa dump user base lalu target specific user via crafted queries ke `notes`, `orders`, `progress`.

**Fix:**
```sql
DROP POLICY service_role_crud ON user_identities;
CREATE POLICY user_identities_self_select ON user_identities
  FOR SELECT USING (email = auth.jwt() ->> 'email');
-- INSERT/UPDATE/DELETE: service_role only (RLS blocks by default if no policy)
```

### C2. `api_keys` & `custom_provider_keys` — `qual: true` on SELECT
```sql
policy: "Service role can read api_keys"
qual: true   -- ❌ any authenticated user can SELECT
```
**Bahaya:** Full leak OpenAI/Gemini/DeepSeek/custom API keys. Attacker pakai key untuk inference atas biaya DeutschUp, atau jual di darkweb. **Same for `custom_provider_keys`.**

**Fix:**
```sql
DROP POLICY "Service role can read api_keys" ON api_keys;
DROP POLICY "Service role can read custom_provider_keys" ON custom_provider_keys;
DROP POLICY "Service role can read custom_models" ON custom_models;
-- Service role bypasses RLS anyway, so this policy is redundant AND dangerous
```

### C3. `study_sessions` RLS — type coercion hole
```sql
qual: user_id = (auth.uid())::text
```
**Bahaya:** Frontend pakai Clerk `user_id` (format `user_xxx`), Supabase auth pakai UUID. Mismatch = policy selalu reject legitimate users (false negative). Tapi kalau ada bug di insert path (user_id dari body tanpa validasi), atau Clerk ID collide via cast, bisa leak data.

**Fix:** Add trigger validate format OR change column type. Quick win:
```sql
-- Force UUID format on insert via CHECK constraint
ALTER TABLE study_sessions
  ADD CONSTRAINT user_id_is_uuid
  CHECK (user_id ~* '^[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$');
-- Better: change user_id to UUID and map Clerk ID via user_identities table
```

## ⚠️ HIGH (H1-H4) — API authorization bypass

### H1. `db-proxy.ts` — `get-orders` ANY user can view anyone's orders
```typescript
case 'get-orders': {
  const userId = req.query.userId as string || req.body?.userId;
  // ❌ No check that caller === userId
  db.from('orders').select('id, status, amount, payment_method, paid_at, created_at')
    .eq('user_id', userId)
}
```
**Bahaya:** Auth user POST `?userId=victim_id` → dump semua paid orders (amount, payment_method, paid_at). Intel untuk social engineering + bukti target punya akun Pro.

**Fix:**
```typescript
const userId = (req as any).user?.id;
if (!userId) return res.status(401).json({ error: 'Unauthorized' });
// Pakai req.user.id langsung, abaikan body/query
```

### H2. `db-proxy.ts` — `get-profile` same issue
```typescript
const userId = req.query.userId as string || req.body?.userId;
db.from('profiles').select('tier, tier_expiry, full_name, role, subscription, pro_expires_at')
  .eq('id', userId)
```
**Bahaya:** Leak profile + role (admin detection) + subscription status user lain.

**Fix:** Same as H1 — pakai `req.user.id`.

### H3. `payment.ts` create — `userId` dari body, bukan dari token
```typescript
const { userId, planType, email, name } = req.body;
// ❌ userId from untrusted body
db.from('orders').insert({ user_id: userId, ... })
```
**Bahaya:** Attacker POST `{ userId: "victim_id" }` → order dibuat atas nama victim. Atau spam orders dengan userId random untuk fill DB.

**Fix:**
```typescript
const userId = (req as any).user?.id;
const email = (req as any).user?.email;
const name = (req as any).user?.full_name;
if (!userId) return res.status(401).json({ error: 'Unauthorized' });
// Abaikan userId/email/name dari body
```

### H4. `payment.ts` webhook — silent degradation = unauth by default
```typescript
if (webhookSecret) {
  // verify signature...
} else {
  console.warn('No BAYARGG_WEBHOOK_SECRET set — skipping signature verification');
}
```
**Bahaya:** Kalau env var lupa di-set (Vercel env rotation, typo), attacker POST:
```json
{ "invoice_id": "ANY", "status": "paid", "final_amount": 49000 }
```
→ User dapet Pro gratis. Atau downgrade user lain dengan `{ status: "refund" }`.

**Fix:**
```typescript
if (!webhookSecret) {
  console.error('[payment/callback] CRITICAL: BAYARGG_WEBHOOK_SECRET not set — refusing to process');
  return res.status(500).json({ error: 'Webhook misconfigured' });
}
// Then verify...
```

## 🟡 MEDIUM (M1-M4) — Authorization + abuse

### M1. `adminMiddleware` — email spoof via body
```typescript
let userEmail = req.user?.email || req.body?.email || req.headers['x-user-email'];
```
**Bahaya:** Kalau gak ada auth token, fallback ke body/header. Attacker POST `{ email: "abdullahalmughiroh@gmail.com" }` ke admin endpoint → bypass.

**Fix:**
```typescript
// Hanya trust JWT-decoded email, JANGAN fallback ke body
let userEmail: string | undefined;
if (req.user?.email) userEmail = req.user.email;
else if (req.headers.authorization?.startsWith('Bearer ')) {
  const payload = decodeJwtPayload(req.headers.authorization.split('Bearer ')[1]);
  if (payload?.email) userEmail = payload.email;
}
// No body/header fallback
```

### M2. `payment.ts` create — no rate limit
```typescript
if (action === 'create') {
  // ❌ no checkRateLimit()
}
```
**Bahaya:** Spam `POST /api/payment?action=create` → orphan `pending` orders + drain Bayar.gg quota.

**Fix:**
```typescript
if (!checkRateLimit(clientIp, 5, 60000)) {
  return res.status(429).json({ error: 'Too many requests' });
}
```

### M3. `api/ai.ts` — `uid` dari unverified JWT claim
```typescript
try {
  const payload = JSON.parse(Buffer.from(token.split('.')[1], 'base64url').toString());
  if (payload.email) uid = payload.email;  // ❌ unsigned
}
```
**Bahaya:** Attacker craft JWT dengan email apapun (gak perlu signature valid karena gak di-verify). Rate limit per-IP bypass via rotating IPs. Logs poisoning pakai email apapun.

**Fix:** Verify signature via Clerk public key, atau reject kalau gak ada valid auth source.

### M4. `db-proxy.ts` `get-session` — info disclosure
```typescript
case 'get-session': {
  const email = req.headers['x-user-email'] as string || req.query.email as string;
  return res.json({ email, provider: 'clerk' });
}
```
**Bahaya:** Email enumeration endpoint. Attacker brute-force valid emails.

**Fix:** Require valid auth, return only `req.user.email`.

## 🛠️ Attack scenarios yang harus ditest post-fix

1. **SQLi via crafted userId** — POST `?userId=' OR 1=1` → must return 401
2. **JWT forgery** — send JWT dengan alg=none, signature=empty → must reject
3. **Webhook replay** — replay old webhook with valid signature → must reject (timestamp check)
4. **RLS bypass via service role leak** — coba akses table yang seharusnya di-block
5. **CORS bypass** — request from evil.com → must not receive data
6. **Email enumeration** — POST `?email=test@x.com` ke db-proxy → must rate limit
7. **Free Pro abuse** — POST payment create tanpa auth → must reject
8. **Admin endpoint bypass** — POST `{ email: "admin@..." }` tanpa token → must reject
